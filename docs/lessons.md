# Lessons

> 状态：living document | 更新：2026-11-14
> 从上一个项目提取的通用失败模式。**不引用旧编号、不假设读者看过旧仓库。**
> 每条都写：现象、根因、规则、怎么验、适用于哪些 feature。

## 使用方式

- 写/改 feature 前，读“适用于”该 feature 的条目。
- 做 review 时，把相关条目当 checklist。
- 新踩的坑：先判断是不是已有条目的变种；是就补充“现象”，不是就新增 `L-xxx`。

## L-001 命令返回 0 不等于生效

**现象**：某步“成功”了，但系统状态没变；或者检查脚本全绿，实际是坏的。
**根因**：工具对“打不开/不存在/跳过”返回 0；或者只看了退出码，没看运行状态。
**规则**：关键步骤必须有可观察证据：`findmnt`、`lvs`、`bootctl list`、`efibootmgr -v`、`journalctl -b`。
**怎么验**：故意制造失败（拔盘、改错 label、给不存在的 root=），确认检查会变红。
**适用于**：F-002、F-003、F-011、F-012。

## L-002 可写 `/etc` 必须在 PID1 之前挂好

**现象**：`machine-id` 是 `uninitialized`；DHCP 报 `-ENOPKG`；journald 不落盘；sysusers/tmpfiles 行为异常。
**根因**：PID1 先读了只读 root 的 `/etc`，之后才挂可写 `/etc`；或者 overlay 的 upper 覆盖了 PID1 的 bind mount。
**规则**：`/etc`（以及 `/var`）在 initrd 里挂好，再 `switch_root`；不要让用户态 systemd 去挂 `/etc`。
**怎么验**：`findmnt /etc`；`cat /etc/machine-id`；重启两次比对；`journalctl -b` 看 machine-id 日志。
**适用于**：F-004、F-005、F-012。

## L-003 内核与根必须成对

**现象**：候选条目和正式条目同名；引导器选中旧内核配新根，或新内核配旧根；系统起不来或行为怪异。
**根因**：kernel/initrd/cmdline 和 root 分区是分开管理的；更新时只换了一半。
**规则**：用 UKI，把 kernel + initrd + cmdline + microcode 打成一个文件；槽 = UKI；更新先写 root，最后写 UKI。
**怎么验**：`bootctl list` 看条目；`/proc/cmdline` 的 `root=` 与当前槽一致；`os-release` 版本与 UKI 一致。
**适用于**：F-002、F-003、F-005。

## L-004 启动条目命名/计数是一个状态机

**现象**：`bootctl set-oneshot` 传了带 `+3` 的名字，one-shot 被静默忽略；或者 bless 后条目名不对；回滚没发生。
**根因**：文件名（`keel-b+3.efi`）和 entry ID（`keel-b`）不是一个东西；boot counting 的 tries-left 在文件名里。
**规则**：候选写 `keel-<slot>+3.efi`；`bootctl set-oneshot` 用不带 `+3` 的 entry ID；成功由 `systemd-bless-boot` 改名。
**怎么验**：`bootctl list` 看 tries-left；故意让候选失败，确认回旧槽；`ls /boot/EFI/Linux` 看 `.failed`/计数条目。
**适用于**：F-003、F-012。

## L-005 共享可写区满会拖垮配置

**现象**：`/var` 或 `/home` 所在的 data 分区写满 → 日志/容器镜像/用户数据都写不进去；如果 `/etc` 还在同一个文件系统上，会连带 machine-id/ssh key 生成失败 → DHCP/IPv6/DNSSEC 一起坏。
**根因**：可写配置和大量数据共享同一个文件系统；没有预留/预算。
**规则**：可写区（`/etc`、data）留 >=10% 空闲；写大块数据前先 `df`；失败要清理；不要把 `/etc` 和日志/镜像/容器存储塞进同一个无上限目录。
**怎么验**：把 `/var` 写满，确认 `/etc` 仍可写；看 `keel-data-guard` 类似的预算逻辑是否触发。
**适用于**：F-004、F-007、F-008、F-014。

## L-006 镜像里不能带机器身份

**现象**：所有机器共用同一个 `machine-id`；SSH 主机密钥相同；DHCP DUID 冲突；克隆后网络异常。
**根因**：构建时生成了 `machine-id`/ssh host key，或者从模板拷贝了 `/etc`。
**规则**：镜像里 `machine-id` 为空；ssh host key 首启生成；安装时清掉模板里的身份文件。
**怎么验**：`cat /etc/machine-id` 每台不同；`ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub` 每台不同。
**适用于**：F-004、F-011。

## L-007 同一份事实不能有构建时/运行时两份

**现象**：构建用的 repart 定义和运行时用的不是同一份；`build.sh` 和 `build-container.sh` 参数漂移；修了一处，另一处仍旧。
**根因**：同一份配置被复制/生成多次；没有单一事实来源。
**规则**：配置只写一份；运行时从构建产物读取；如果必须生成，生成器和消费者用同一个输入，并加断言。
**怎么验**：改一处配置，确认所有路径都变；对比生成物；grep 是否还有第二份。
**适用于**：F-001、F-004、F-011。

## L-008 上游默认值是隐式契约

**现象**：脚本被默认 initrd 继承；`gpt-auto` 静默不挂 ESP；`Initrds=` 是替换不是追加；某个工具“没有配置”时行为与预期相反。
**根因**：把“文档没写”当成“不会发生”；没有读源码/实测。
**规则**：每个上游工具的关键默认值都要在 `verification.md` 里有一条假设；用 `--dry-run`/最小复现确认；不靠记忆。
**怎么验**：读 man/源码；做最小实验；记录版本号。
**适用于**：F-001、F-005、F-011。

## L-009 initrd 的“冻住”和“panic”是两类失败

**现象**：内核 panic 会重启；PID1 冻住/停在 emergency 不会；机器永久挂起，远程无法恢复。
**根因**：只配了 `panic=-1`，没有看门狗；或者看门狗在 initrd 里没生效。
**规则**：`panic=-1` + 运行时看门狗 + emergency 超时重启；initrd 也要有超时/看门狗；三类失败都要演练。
**怎么验**：QEMU 里分别制造 panic、PID1 冻住、停在 emergency，确认 60-120 秒内复位。
**适用于**：F-003、F-005、F-012。

## L-010 元数据备份不能只放在被保护对象里

**现象**：LVM/加密/RAID 的元数据备份放在同一个 VG/分区里；对象坏了，备份也读不到。
**根因**：备份路径在故障域内。
**规则**：LVM 元数据备份放 ESP/USB；`vgcfgbackup -f` 指到 system VG 之外；定期验证 `vgcfgrestore`。
**怎么验**：QEMU 里破坏 VG 元数据，从 ESP 备份恢复；确认 LV 回来了。
**适用于**：F-004、F-012、F-014。

## L-011 shell 状态机不可维护

**现象**：一个 500-700 行的 shell 库管理更新/回滚/状态；条件分支越来越多；错误处理靠 `|| true`；没人敢改。
**根因**：用 shell 写有状态、有顺序、有失败恢复的逻辑。
**规则**：关键逻辑编译（C/C++/Rust）；shell 只做胶水；更新器、状态工具、安装器都编译。
**怎么验**：代码 review 看是否有 `if/else` 状态机、全局变量、`eval`；单元测试覆盖失败路径。
**适用于**：F-003、F-011、F-013。

## L-012 校验器自己会说谎

**现象**：`grep` 锚点失效；`debugfs` 对打不开的文件返回 0；guest 正常 poweroff 让演练返回 0；非 root 时整节检查静默消失。
**根因**：校验的是源码文本/退出码，不是运行状态；工具语义与假设不符。
**规则**：校验运行状态；每个检查有“故意变坏”测试；非 root/缺工具要报失败，不静默跳过。
**怎么验**：做定向变异（删一行、改一个路径），确认检查变红；在非 root 下跑一遍。
**适用于**：全部。

## L-013 不签名就必须关 Secure Boot

**现象**：自制 systemd-boot/UKI 在开了 Secure Boot 的机器上根本不执行；看起来像“镜像坏了”。
**根因**：固件只信任签名链。
**规则**：v1 不签名 → 固件里关 Secure Boot；文档写清；未来做 F-010 时再打开。
**怎么验**：`bootctl status` 看 `Secure Boot: disabled`；固件设置里确认。
**适用于**：F-001、F-002、F-010。

## L-014 空间不足要 fail closed

**现象**：下载/写盘写到一半 ENOSPC；留下半个镜像/半个 UKI；下次启动发现根不完整。
**根因**：没有先问空间；失败后没有清理；写入顺序让“入口点”先落盘。
**规则**：写大块数据前 `df`/查分区大小；先写临时文件/非活动槽；入口点最后写；失败清理。
**怎么验**：把目标分区/ESP 填到只剩一点，确认更新被拒绝且旧槽仍可启动。
**适用于**：F-003、F-011、F-014。

## L-015 文档和断言要定期对抗复核

**现象**：文档说“已 mask”，代码已经解封；文档说“ext4 内建”，实际是模块；断言一直空跑。
**根因**：文档/断言没有和代码/实测一起更新；没有对抗复核。
**规则**：每个版本收口时做一次“文档 vs 代码 vs 实测”对照；断言要有反向测试；过时说法直接删/改。
**怎么验**：随机抽 5 条文档声明，逐条用命令验证；抽 5 条断言，做定向变异。
**适用于**：全部。

## L-016 文件权限会跟着仓库进镜像

**现象**：仓库里 `0600` 的 networkd 配置进镜像后，网络静默不工作；`sudo` 的 setuid 丢失。
**根因**：构建系统保留源文件权限；复制时没有显式 `chmod`。
**规则**：进镜像的文件权限在构建脚本里显式设置；安装后回读断言；不要依赖“我本地是 0644”。
**怎么验**：`stat -c '%a %U:%G'` 关键文件；`find` 检查非预期 0600。
**适用于**：F-001、F-004、F-011。

## L-017 宿主环境假设会漏进脚本

**现象**：脚本写死 `#!/bin/bash`，宿主没有 `/bin/bash`；非 root 时 `PATH` 缺 `/usr/sbin`，整节检查消失。
**根因**：把开发机当成所有环境。
**规则**：脚本用 `/usr/bin/env` 或 POSIX sh；显式设置 `PATH`；缺工具报失败；文档写“在哪个环境跑”。
**怎么验**：在最小容器/非 root/不同发行版上跑一遍。
**适用于**：F-001、F-011、F-012。
